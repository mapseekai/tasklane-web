# Where the page list and the navigation live

## Navigation source per generator

The file tree gives you the pages; the generator's config gives you the intended navigation. Comparing the two is what exposes orphans and dead entries.

| Generator              | Navigation source                                  | Notes                                                                               |
| ---------------------- | -------------------------------------------------- | ----------------------------------------------------------------------------------- |
| MkDocs / Material      | `mkdocs.yml` → `nav:`                              | A bare directory entry (`user-guide/`) pulls in everything below it                 |
| Docusaurus             | `sidebars.js` / `sidebars.ts`, `_category_.json`   | `autogenerated` sidebars follow the folder tree and front-matter `sidebar_position` |
| Sphinx / Read the Docs | `toctree` directives from `index.rst`              | Pages outside every toctree raise build warnings - read the build log               |
| VitePress              | `.vitepress/config.*` → `themeConfig.sidebar`      | Sidebar keyed by URL prefix                                                         |
| Mintlify               | `docs.json` → `navigation` (older: `mint.json`)    | Explicit list; anything unlisted is unreachable                                     |
| Astro Starlight        | `astro.config.*` → `starlight({ sidebar })`        | Supports autogenerate per directory                                                 |
| Nextra                 | `_meta.json` per folder                            | Order and titles both live here                                                     |
| GitBook                | `SUMMARY.md`                                       | The summary _is_ the nav                                                            |
| Docsify                | `_sidebar.md`                                      | Per-folder sidebars possible                                                        |
| Hugo / Docsy           | front-matter `weight`, section `_index.md`         | No central nav file; order is distributed                                           |
| Jekyll / Just the Docs | `_data/navigation.yml` or front-matter `nav_order` | Mixed sources are common                                                            |

Front matter matters as much as the config in several of these: `sidebar_position`, `nav_order`, `weight`, `draft`, `hidden` and `unlisted` all change what a reader sees.

## No repository access

Crawl instead, and label the inventory as nav-only:

1. Fetch `sitemap.xml` for the full URL set, and the rendered navigation for the intended tree.
2. Diff them: URLs in the sitemap but not in the nav are orphan candidates.
3. Accept the limits - you cannot see drafts, hidden pages, front matter or last-modified dates, so drop staleness and orphan measures from the scorecard rather than guessing them.

If neither a repository nor a live site is reachable, ask the user to paste the navigation tree and work from titles alone; say in the report that classification came from titles, which is the weakest evidence available.

## Inventory script

`scripts/docs-inventory.py` walks the docs tree and emits one row per page with the facts the classification pass needs.

```bash
# Markdown docs with a MkDocs nav
python3 scripts/docs-inventory.py ./docs --nav mkdocs.yml > inventory.tsv

# Docusaurus, several nav sources, JSON for further processing
python3 scripts/docs-inventory.py ./docs --nav sidebars.ts --nav docusaurus.config.ts --format json

# Sphinx project, ignore stubs under 50 words
python3 scripts/docs-inventory.py ./doc --ext .rst,.md --nav doc/index.rst --min-words 50
```

Columns: `path`, `title`, `words`, `headings`, `max_heading_depth`, `code_blocks`, `numbered_steps`, `imperatives`, `option_table`, `questions`, `internal_links`, `external_links`, `in_nav`, `last_modified`. Orphan candidates are printed to standard error so they stay out of the TSV.

Reading the columns:

- `numbered_steps` + `imperatives` high, `option_table` 0 → action content: tutorial or how-to.
- `option_table` 1 with few steps → reference.
- Long, few code blocks, few steps → explanation, or an over-long page hiding several modes.
- `numbered_steps` high **and** `option_table` 1 → mixing candidate; open the page.
- `words` above ~2,500 with `max_heading_depth` ≥ 4 → a page that has absorbed several modes.
- `in_nav` `no` → orphan candidate; confirm against front matter (a `draft`/`unlisted` page is intentional).

The nav matcher is heuristic across generators: it extracts path-like tokens from any config format and matches by stem. Confirm orphan candidates before reporting them, and skip the `--nav` flag entirely for generators whose order lives in front matter (Hugo, Jekyll), where it produces noise. The columns are a shortcut, not a requirement - the hand-built fallback is in SKILL.md Step 2.
