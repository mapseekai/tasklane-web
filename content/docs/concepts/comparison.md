在构建前端高负载计算或 Node.js 密集型任务时，开发者往往面临多种技术选型。理解 tasklane 与同类工具在**设计目标、抽象层级与资源控制粒度**上的本质差异，有助于在架构设计中做出最合理的决策。

```
┌───────────────────────────────────────────────────────────────┐
│                      技术选型象限划分                          │
├───────────────────────────────┬───────────────────────────────┤
│          轻量 RPC 通信         │          专业资源调度          │
│       Comlink, threads.js     │            tasklane           │
│   (函数调用代理 / 无背压无配额)   │   (五类预算 / 背压 / 租约生命周期) │
├───────────────────────────────┼───────────────────────────────┤
│          裸底层接口            │         持久化分布式队列       │
│  原生 Web Worker / Node 线程池  │       BullMQ, Temporal        │
│   (无排队控制 / 易导致 OOM)     │   (跨网络跨进程 / 依赖外部存储)    │
└───────────────────────────────┴───────────────────────────────┘
```

## 核心特性横向对比矩阵

| 特性维度 | 原生 Web Worker / Threads | Comlink / threads.js | Piscina / workerpool | tasklane |
| :--- | :--- | :--- | :--- | :--- |
| **核心抽象** | 原始事件监听 (`postMessage`) | 远程过程调用 (RPC 代理) | 线程池与并发任务队列 | **资源受限环境下的契约化调度器** |
| **五类资源预算** | ❌ 无限制 | ❌ 无限制 | ⚠️ 仅任务超时/线程数 | ✅ **严格受控：`inputBytes`、`scratchBytes`、`outputBytes`、`cacheBytes`、`residentBytes`** |
| **背压流控** | ❌ 消息盲发，积压无感知 | ❌ 仅 Promise 等待 | ⚠️ 依赖队列长度阈值 | ✅ **动态负载反馈与拒收机制** |
| **数据所有权管理** | ⚠️ 手动传递 transfer 数组 | ⚠️ 手动标记 `Comlink.transfer` | ⚠️ 手动处理 | ✅ **ResultLease 零拷贝租约与纪元锁定** |
| **生命周期与取消** | ⚠️ 手动终止整个 Worker | ❌ 缺乏标准协作式取消 | ⚠️ 支持 AbortSignal 丢弃 | ✅ **分级取消与检查点 (`checkpoint`) 让出** |
| **惰性与准备阶段** | ❌ 主线程必须提前准备数据 | ❌ 参数立即序列化 | ❌ 立即投递 | ✅ **`prepare` 延迟构建（超载不占内存）** |
| **双端统一架构** | ❌ 浏览器与 Node API 不兼容 | ⚠️ 需不同适配层 | ❌ 主要是 Node.js 端 | ✅ **核心协议同构，适配器解耦** |
| **可观测性与血统** | ❌ 无内置监控 | ❌ 无内置监控 | ⚠️ 基础线程指标 | ✅ **内置探针与协议版本溯源 (Provenance)** |

## 深度对比剖析

### 1. 对比原生 Web Worker / worker_threads

原生 Worker 提供了最纯粹的硬件多线程支持，但在企业级高并发场景中直接使用原生 API 会面临以下致命痛点：

- **无内存与传输上限（OOM 风险）**：直接向 Worker 盲目 `postMessage` 大对象，主线程无法预知 Worker 的内存负载。当高频触发计算时，消息积压会导致整个浏览器标签页崩溃崩溃（Out of Memory）。
- **缺乏协作式中断机制**：原生 API 只提供了粗暴的 `worker.terminate()`。一旦终止，Worker 内所有上下文和已初始化的 WASM/模型全部丢失，无法仅取消某个超时任务而保留 Worker 实例。
- **Transferable 容易悬空**：主线程转移 `ArrayBuffer` 之后，主线程对应内存立即被剥离（ByteLength 变为 0）。在没有严格生命周期契约时，极易发生“主线程误读已失效 Buffer”或“Worker 异常退出后内存彻底丢失”的问题。

> **tasklane 的升级点**：将裸线程封装为受管资源，提供声明式五类预算，支持在不杀死 Worker 的前提下优雅取消单个任务，并通过 `ResultLease` 保护结果所有权。

---

### 2. 对比 Comlink 与 RPC 代理库

[Comlink](https://github.com/GoogleChromeLabs/comlink) 是一个优秀的 RPC 库，它的设计核心是**抹平通信复杂度**，让调用 Worker 像调用本地异步函数一样自然。

- **解决的问题不同**：Comlink 解决的是“如何方便地通信与调用函数”，而 tasklane 解决的是“在机器资源受限时，如何防止系统被压垮、如何公平调度、如何保证数据不泄露”。
- **缺乏流控与排队**：如果主线程短时间内调用了 1,000 次 RPC 函数，Comlink 会直接向底层发送 1,000 条消息，缺乏并发槽位（Slot）限制与背压拒收能力。
- **无资源预检机制**：Comlink 必须在主线程将入参完整序列化。如果调度队列已满，这些参数对象会一直滞留在内存中；tasklane 提供了 `prepare()` 闭包机制，任务排到空闲 Slot 之前，巨额数据根本不会在内存中实例化。

---

### 3. 对比 Piscina / workerpool 等线程池库

[Piscina](https://github.com/piscinajs/piscina) 和 `workerpool` 是 Node.js 生态中非常成熟的线程池管理工具。

- **适用场景偏向**：Piscina 针对 Node.js 服务端高吞吐设计，深度优化了线程复用。
- **资源维度的差异**：传统线程池通常只关注“线程总数”和“队列长度”。tasklane 提出了**五类细粒度内存预算（`inputBytes`、`scratchBytes`、`outputBytes`、`cacheBytes` 与 `residentBytes`）**，全链路拦截输入数据、运行暂存空间、未消费结果以及常驻缓存，并在并发槽位（Slot）与租约生命周期上实施严格的超时和熔断保护。
- **结果租约机制**：传统线程池在任务返回后直接移交结果。tasklane 引入了 `ResultLease`，支持在结果返回后由调用方主动锁定（Retain）或释放（Release），并带有时钟与纪元（Epoch）保护，防止大对象在主线程内存中长期无序滞留。

---

### 4. 对比 BullMQ / Temporal 等分布式任务队列

[BullMQ](https://bullmq.io/) 与 [Temporal](https://temporal.io/) 是行业标准的分布式任务编排与持久化队列：

- **物理边界完全不同**：BullMQ 和 Temporal 依赖外部服务（Redis、PostgreSQL、Temporal Server），用于**跨服务器、跨进程、持久化、支持长达数天断点续跑**的业务流。
- **性能开销层级**：分布式队列每次投递伴随网络 I/O、磁盘持久化与 Redis 命令序列化，延迟在毫秒甚至秒级；tasklane 是**单机进程/线程内硬件级吞吐**，通信延迟在微秒级，专为前端富客户端与单节点密集型数据处理设计。

## 选型决策指南 (Decision Tree)

{{< diagram name="comparison" alt="后台计算方案选型对照" >}}

### 何时应该选用 tasklane？
1. **浏览器端重计算**：如在线音视频剪辑、大体积 Excel/CSV 文件解析、图像滤镜处理、CAD/3D 几何网格计算；
2. **需要强力防内存溢出 (OOM)**：页面不能因为突发的大文件或高频点击而崩溃，必须在前端实现严格的五类预算拦截；
3. **高频任务流与需要协作式取消**：用户在界面连续搜索、缩放画布或切换切片，前一个昂贵计算必须能在毫秒级安全让出 Worker 资源；
4. **双端同构需求**：同一套计算核心逻辑需要同时在 Vite 浏览器端和 Node.js 后端服务中平滑运行。

### 何时不需要 tasklane？
1. 仅偶尔执行一次耗时仅几毫秒的简单函数计算（原生 Worker 或 Comlink 足够轻巧）；
2. 跨集群的订单结算、支付回调、需跨天重试的持久化业务流程（请使用 Temporal 或 BullMQ）。
